# 视觉开放词表定位能力：可行性分析与 V1.1 规划（未实现，规划项）

> **状态声明（防误解）**：本文是**技术前瞻与规划**，截至当前版本（V1.0 / 交付包）**尚未实现任何视觉检测代码**，
> 系统内不存在相关接口、模型权重或前端功能。答辩与商业材料中**不得表述为本项目已具备该能力**。
> 本文用途：说明为什么这条路线与现有架构契合、落地需要哪些前置条件、以及分阶段计划与风险边界。

## 一、被评估的对象

**NVIDIA LocateAnything-3B**（2026-05-26 开源，模型页 `nvidia/LocateAnything-3B`）：
一个 3B 参数的**开放词表视觉定位（open-vocabulary grounding）**模型，输入"图片 + 任意类别词表"或
"指代式提问"（如"戴红安全帽的工人"），输出**结构化标签 + 边界框坐标**。

架构（据公开资料）：Eagle VLM 栈 = MoonViT 动态分辨率视觉编码器 + Qwen2.5-3B 语言骨干 + 并行框解码头
（`la_flash` 加速核未编译时退化为自回归逐 token 输出框）。

**第三方实测（InferenceBench，2026-09-14，RTX 4000 Ada 12GB / BF16 / SDPA，1600px 输入）**：

| 指标 | 实测值 | 说明 |
|---|---|---|
| 峰值显存 | **9.7–11.1 GB** | 随输入分辨率增长；640px 约 8.5GB；4K 不可行 |
| 单图延迟 | **7.4–19 s**（多类别）；7.4–13.5 s（指代查询） | 延迟与**输出框数量**成正比，与图像尺寸关系较小 |
| 密集场景故障 | 仓库场景 ~15 个箱子输出 **328 个框**、51.7s | 自回归"框循环"，需限制 `max_new_tokens` 或用 `la_flash` |
| 缺失类别行为 | 返回 `None`，**不编造低置信框** | 对审计类流程是安全属性 |
| 建筑/工地场景 | 检出 6 人、4 安全帽、4 反光背心、塔吊、2 台挖掘机 | 与本项目矿山场景高度同构 |
| 加速空间 | 官方称并行解码头 ~2.5× 加速（未在本实测中编译验证） | 编译通过后单图可望进入 10s 内 |

**来源**：[InferenceBench 12GB 实测](https://inferencebench.io/blog/locate-anything-3b-laptop-benchmark)、
[模型页](https://huggingface.co/nvidia/LocateAnything-3B)、[中文报道](https://tech.ifeng.com/c/8tXnk50rBKo)、
[CPU/GGUF 移植](https://github.com/mudler/locate-anything.cpp)。

> 上表为**第三方数据**，落地前必须在本机复测（见 §五 前置验证清单）。本文不把这些数字当作本项目指标。
> 补充说明：本机实测中 HuggingFace 模型页直接抓取失败（网络可达性问题），
> 说明**权重下载路径需提前打通**（镜像/代理/离线拷贝），这也是 §五 清单第 6 项"离线交付验证"存在的原因。

## 二、与 ICOPS 现有架构的契合点

现有系统在"感知"维度只有**结构化遥测 + 文本**，现场照片无处可去——这是当前能力版图上最明显的一块空白。
视觉开放词表定位正好补这个入口，且**不推翻任何既有设计**：

| 现有资产 | 与视觉定位的衔接方式 |
|---|---|
| 设备参数库 / 维保知识库（`kb_type=equipment/maintenance`） | 框出"液压缸/轮胎/履带" → 关联该部件知识条目 → 触发既有诊断逻辑 |
| 工单六状态机 + `oms_work_order_event` 时间线 | 检测结果与照片作为**工单证据附件**，形成"视觉证据 → 处置 → 归档"闭环 |
| 防幻觉三道防线（数字不出模型、陈述必有出处、人工确认标注） | 模型"缺失类别返回 None 而非硬猜"的特性与之一致；检测结果同样标注"需人工确认" |
| 电子围栏告警（`MapMonitor`） | 坐标判断 + 视觉二次确认，降低误报；可覆盖"有人未戴安全帽"这类坐标看不见的问题 |
| Agent 编排（单入口 + 意图路由） | 新增"图像意图"分支即可，专业智能体不横向互调的原则不变 |
| 容灾网关模式（`llm_gateway` 主备 + 离线回退） | 视觉侧复用同一模式：本地 GPU 模型 → 视觉 API → **离线确定性回退（不编造框）** |

## 三、拟议的四个应用场景（按价值排序）

**① 巡检照片 → 部件缺陷 → 自动工单（首选）**
现场人员/巡检机器人/无人机拍照上传 → 开放词表定位部件 → 与知识库对应条目关联 → 生成维修工单并附照片证据。
价值：把"巡检发现"从口头描述变成可检索、可追溯、可统计的数字化记录。

**② 安全合规巡检（与围栏联动）**
人员、安全帽、反光背心、车挡、警戒带、边坡落石区域。价值：安全管理的直接抓手，且演示观感强。

**③ 场区航拍 → 设备定位 → 数字孪生**
从航拍图定位挖掘机/矿卡并映射到站点坐标。**难点不在模型而在标定**：单目图像需已知相机位姿或地面控制点
（GCP）才能像素→世界坐标，属额外工程量，建议排在① ②之后。

**④ 明确不做的事**
* 不用它替代现有预测性维护模型（视觉定位是感知模型，不做时序预测）；
* 不用它回答已有结构化数据能回答的问题（数字仍走数据库直读，防幻觉第一道防线不破）。

## 四、三条硬约束（必须如实披露）

1. **许可证：NVIDIA 非商业研究许可**。据第三方分析，可用于内部演示、研究原型、学术工作；
   **不得**直接嵌入对外销售的产品/SaaS，或以其输出获取直接商业收入，除非与 NVIDIA 签署商业协议。
   * 对本项目（参赛演示）：**演示与评审场景属合规用途**；
   * 对商业模式章节：**不得**把该视觉能力计入可售功能或收入模型；
   * 商用安全替代路线（许可证需在选型时逐个复核原文）：OWLv2 / GroundingDINO（通常 Apache-2.0）、
     Florence-2（MIT），或基于宽松许可骨干自建轻量检测模型。
2. **硬件与延迟（本机实测：跑不了，需升级硬件）**：该模型实测需 **≥12GB 显存**（峰值 9.7–11.1 GB），
   单图 7–19s（未编译加速核）。**本机 GPU 实测为 NVIDIA RTX 4060 Laptop、8188 MiB（8 GB）**
   —— 低于该模型的实测峰值下限，**当前机器无法运行 LocateAnything-3B**（此结论由本次环境实测更正，
   此前按"≥12GB"记录属于未核实）。若确需视觉能力，路径有三：
   * 升级到 ≥12GB 显存机型（或 16GB 更稳妥），并按 §五 清单复测峰值；
   * 改用更小的开放词表检测模型（OWLv2 / GroundingDINO，显存需求更低，同样需实测）；
   * 维持现状：**不做视觉**，所有巡检仍以结构化数据 + 人工录入承载。
   另：本项目现状是 **CPU 优先、断网可演示**；权重数 GB 必须预下载并纳入离线交付包，
   否则破坏"断网可演示"原则；无 GPU 环境下只允许走 CPU GGUF 批处理或**直接降级为"无视觉"**，
   绝不用假结果填充。
3. **中文提示词能力待实测**：语言骨干为 Qwen2.5-3B，中文理论上可用，但官方演示场景以英文提示为主。
   **在实测通过之前，不得宣称支持中文开放词表**；前端提示词的给出方式（预设部件词表 vs 自由输入）
   需按实测召回率决定。

## 五、落地前置验证清单（V1.1 启动前必须完成）

| # | 验证项 | 通过标准 | 不通过时的处置 |
|---|---|---|---|
| 1 | 许可证原文核对 | 取得 NVIDIA 许可条款原文并归档，确认演示/评审用途边界 | 切换宽松许可替代模型 |
| 2 | 本机显存与延迟复测 | ≥12GB 显存可加载；常用巡检图（≤1600px）单图 ≤20s | 降分辨率 / 缩小词表 / 改批处理 |
| 3 | 中文提示词召回对照 | 中文与英文提示在矿山场景图上召回率差异可接受（目标：关键部件 ≥90%） | 前端固定预设词表（英文映射），不开放自由输入 |
| 4 | 密集场景稳定性 | 限制 `max_new_tokens` 后无"框循环"，或 `la_flash` 编译成功 | 强制上限 + 结果去重（NMS）|
| 5 | 矿山场景域适配 | 在自采/公开矿山照片上验证挖掘机、矿卡、铲斗、履带、轮胎、安全帽等词表召回 | 缩小到已验证的少数类别，或补少量标注微调 |
| 6 | 离线交付验证 | 权重预置后断网可完成一次完整"照片→工单"演示 | 演示脚本改为提前录屏/截图说明 |

## 六、拟议架构（沿用现有容灾模式，可回退）

```
照片上传 ──► VisionProvider（三级容灾）
              ├─ ① 本地 GPU：LocateAnything-3B（研究/演示用途）
              ├─ ② 视觉推理 API（如配置，商用场景走宽松许可服务）
              └─ ③ 离线确定性回退：不做视觉推断，明确返回"未启用视觉能力，需人工确认"
                    （禁止编造任何框或缺陷结论——延续防幻觉第一道防线）
             │
             ▼
      结构化结果（部件标签 + 框 + 置信度 + 模型版本 + 是否降级）
             │
             ├─► 关联 kb_type=equipment/maintenance 知识条目（RAG 引用）
             ├─► 缺陷判定 → 生成维修工单（复用六状态机）+ 照片证据附件
             └─► 前端照片巡检区：框选叠加、证据链展示、人工确认/驳回
```

接口（规划）：`POST /api/vision/detect`（开放词表检测）、
`POST /api/vision/inspection`（照片 → 部件 + 缺陷 + 知识条目 + 是否建单）、
`GET /api/vision/status`（模型/降级状态，与 `/api/llm/status` 同构）。

## 八、口径统一（答辩用）

* **可以说**："我们评估了 NVIDIA LocateAnything-3B 这条开放词表视觉定位路线，它与现有'防幻觉 + 容灾 + 工单闭环'
  架构天然契合，已列入 V1.1 规划，并已完成许可证与硬件前置条件分析。"
* **不能说**："我们已经实现了照片识别/缺陷检测/视觉巡检"（未实现）。
* **不能说**："用了这个模型就能商用"（非商业研究许可，商用需替换或许可协议）。
* **不能说**："中文开放词表已支持"（待实测）。

> 一句话总结：**方向契合、演示可行、商用受限、中文待验**——所以这一版把它写成规划与风险分析，
> 而不是塞一个未经验证的模型进交付包。
